# 0002 — Self-hosted инфраструктура на VPS

**Статус:** принято (2026-07-02)

## Контекст

Проект — учебный: цель автора стать фулстеком и углубиться в бэкенд,
инфраструктуру и систем-дизайн, применив их на практике. «Production» здесь
означает **прод-грейд качество кода и инфры**, а не обслуживание масштаба —
единственный пользователь — сам автор. Значит, критерий выбора инфраструктуры —
не «меньше возни / дешевле», а «больше практики инфры».

## Рассмотренные варианты

1. **Managed PaaS + managed БД** (Fly/Railway + Neon/Supabase).
   - + Минимум эксплуатации, быстрый деплой, бэкапы/TLS/патчи «из коробки».
   - − Прячет именно тот слой, ради которого затеян проект; учебной ценности по
     инфре почти нет.
2. **Self-hosted на VPS** (Hetzner), всё в Docker своими руками.
   - + Максимум практики: контейнеризация, reverse-proxy + TLS, CI/CD,
     самостоятельный Postgres, бэкапы + restore-драйлы, наблюдаемость.
   - − Больше первичной настройки; эксплуатация (аптайм, патчи) на себе.
   - Риск (потеря БД) снимается бэкапами — и это тоже учебный навык.

## Решение

**Self-hosted на VPS**, всё своими руками в Docker. Инфраструктура —
отдельный полноценный под-проект (свой цикл спека → план → реализация):
Dockerfile'ы приложения, `docker-compose.prod`, Caddy (авто-TLS через
Let's Encrypt), CI/CD автодеплой (расширяем существующий GitHub Actions),
Postgres в Docker с бэкапами и учебными restore-драйлами, наблюдаемость
(structured logs + метрики).

**Явно НЕ делаем** преждевременный масштаб: никаких k8s/шардинга/multi-region
под одного пользователя — это карго-культ, а не систем-дизайн. Продвинутое
(Ansible/Terraform, k3s) — только как осознанные учебные упражнения.

## Последствия

- Нужен VPS (Hetzner, ~€4–8/мес) и базовая настройка сервера.
- Ответственность за бэкапы, патчи, TLS, мониторинг — на нас (это и есть цель).
- БД — self-hosted Postgres в Docker (см. [[0001-postgresql-over-sqlite]]),
  без managed-сервиса.
- Ключевые инфра-решения фиксируем новыми ADR по мере реализации.
