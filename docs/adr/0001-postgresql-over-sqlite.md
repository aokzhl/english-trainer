# 0001 — PostgreSQL вместо SQLite

**Статус:** принято (2026-07-02)

## Контекст

Изначально WordForge (v1) использовал SQLite + `better-sqlite3`. При развороте
в платформу курсов (v2) продукт строится прод-грейд ради практики бэкенда и
инфраструктуры (проект учебный, единственный пользователь — автор). Модель
данных на момент решения ещё не написана — построена только авторизация, —
поэтому смена СУБД сейчас максимально дешёвая.

## Рассмотренные варианты

1. **Остаться на SQLite** (возможно, Turso/libSQL для «прод»).
   - + Ноль эксплуатации, уже работает, тесты на `:memory:` тривиальны.
   - − Прячет ровно тот слой (DB-ops, репликация, прод-БД), который хочется
     освоить; один писатель; не тот опыт, что нужен для целей обучения.
2. **PostgreSQL, self-hosted.**
   - + Индустриальный стандарт; учит настоящему DB-ops (бэкапы, восстановление,
     тюнинг, миграции на деплое); родной `pgvector` на будущее для ИИ-семантики.
   - − Async-драйвер → рефактор синхронного кода; нужен запущенный Postgres в
     dev; тесты сложнее, чем `:memory:`.

## Решение

**PostgreSQL** через Drizzle `pg-core` + драйвер `postgres.js`. Существующий
слой БД авторизации мигрируется с SQLite (включая перевод синхронных вызовов
`better-sqlite3` в async). Тесты — **PGlite** (встроенный Postgres в процессе),
что сохраняет быструю схему «свежая БД на тест-файл» без внешнего сервера.

## Последствия

- `createDb`, `buildApp` и функции модуля `auth` становятся async.
- Уходит native-build gotcha `better-sqlite3` (остаётся только `bcrypt` в
  `onlyBuiltDependencies`).
- Появляется зависимость dev/прод от запущенного Postgres (docker-compose).
- Открыт путь к `pgvector`, если ИИ дорастёт до семантического поиска.
- Тип таймстемпов — `timestamptz`, в коде как JS `Date` (Drizzle `mode: 'date'`).
