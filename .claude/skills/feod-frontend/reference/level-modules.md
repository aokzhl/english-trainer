# Уровень Modules — сердце приложения

«Модули — сердце всего приложения. Все остальные уровни созданы только ради
этого». Модуль реализует бизнес-функцию комплексно: переиспользуемая логика,
интеграции между компонентами, взаимодействие с другими модулями.

Философия: **модуль = npm-пакет** — самостоятельная единица, которую можно
перенести в другой проект. Чем менее модуль зависим, тем проще его
переиспользовать и тестировать.

## Критерии: элемент относится к modules, если

- реализует комплексную переиспользуемую логику;
- является подмодулем другого модуля;
- требует взаимодействия с другими модулями;
- представляет сложный модуль с бизнес-логикой;
- требует нескольких файлов для реализации функциональности.

## Структура модуля

```
modules/
└── Training/
    ├── modules/            # подмодули (фрактальность)
    │   └── Flashcards/
    ├── components/         # React-компоненты модуля
    ├── store/              # MobX-стор(ы)
    ├── api/                # запросы к эндпоинтам домена + DTO
    ├── types/
    ├── utils/
    ├── README.md           # назначение, использование, ответственные
    └── index.ts            # ЕДИНСТВЕННАЯ точка входа
```

**FEOD не настаивает на внутренней структуре модуля** — только на публичном
API (`index.ts`) и папке `modules/` для подмодулей. Внутри — свобода,
при единообразии с остальным проектом.

## Публичный API — index.ts

«Никто не может напрямую влезать в сущности модуля, кроме `index.ts`».

```typescript
// modules/Training/index.ts — экспортируй ТОЛЬКО необходимое
export { FlashcardView } from './components/FlashcardView'
export { trainingStore } from './store/trainingStore'
export type { SessionCard, ReviewResult } from './types/training.types'
export { trainingRoutes } from './routes'
```

```typescript
// ❌ ЗАПРЕЩЕНО из другого модуля/страницы:
import { srsInterval } from '@/modules/Training/utils/srs'
// ✅ Правильно:
import { trainingStore } from '@/modules/Training'
```

Подмодуль реэкспортируется так: `export { Flashcards } from './modules/Flashcards'`.

## Подмодули и фрактальность

Подмодули подчиняются тем же правилам, что и модули верхнего уровня.
Вложенность не ограничена технически, но **глубже 3 уровней — крайне не
рекомендуется**.

Правила доступа (жёсткие):
- модуль НЕ может обращаться к подмодулям своего подмодуля («через голову»);
- модуль НЕ может обращаться к подмодулям других модулей;
- модуль МОЖЕТ обращаться к своим прямым подмодулям и нижележащим уровням;
- подмодуль МОЖЕТ импортировать части родительского модуля, но родитель
  внутренности подмодуля — только через его `index.ts` (риск циклических
  импортов). Лучше делать подмодули полностью автономными — тогда их можно
  безболезненно переносить.

Масштабирование — фрактальностью, а НЕ новыми горизонтальными слоями:

```
modules/Billing/
  modules/Invoices/
  modules/Payments/
```

## Кросс-модульное взаимодействие и IoC

Главная опасность модульной архитектуры — сильная связанность между модулями
и неопределённые зависимости. Правило: **минимизировать кросс-модульные
импорты**, предпочитая Inversion of Control.

> Конкретная реализация IoC для сторов/сервисов в этом проекте — DI через
> React-контекст (фабрика `createX(deps)` + провайдер + `useDi`-хук, сборка в
> composition root `app`). Используй её по умолчанию: `reference/di-and-core.md`.
> Там же — про модуль `core` (фундаментальные модули: session, feature-flags,
> i18n) и про то, когда кросс-сквозную единицу кладут в `common`, а не в `core`
> (если её читают из `common`, напр. theme и dialog-manager).

Вариант 1 — зависимость параметром (интерфейс вместо импорта):

```typescript
interface NotificationService {
  notify(message: string): void
}

export function createTrainingStore(notifications?: NotificationService) {
  const notify = notifications?.notify ?? console.log
  // ...
}
```

Вариант 2 — сервис-локатор внутри модуля, реализацию подставляет app:

```typescript
// modules/Notifications/index.ts — модуль объявляет контракт
export interface NotificationService {
  showSuccess(message: string): void
  showError(message: string): void
}

let service: NotificationService

export function setNotificationService(s: NotificationService) { service = s }
export function getNotificationService(): NotificationService {
  if (!service) throw new Error('Notification service not initialized')
  return service
}

// app/integrations/notifications.ts — app внедряет реализацию
import { setNotificationService } from '@/modules/Notifications'
import { ToastService } from '@/modules/ToastUI'
setNotificationService(new ToastService())
```

Преимущества: явные зависимости, лёгкая подмена в тестах, слабая связанность,
замена реализации без изменения модулей.

## Специальные виды модулей

### Однофайловый модуль

`modules/logger.ts` — допустим для маленькой логики, когда полноценный модуль
нецелесообразен. Документация — комментарием в начале файла.
Однофайловые ПОДмодули — не рекомендуются.

### Сквозной модуль

Несколько подмодулей делят одно приватное ядро `_/`:

```
modules/
  package-manager/
    _/          # приватное ядро — доступно ТОЛЬКО подмодулям этого модуля
    npm/
    yarn/
    pnpm/
```

Извне можно импортировать подмодули напрямую:
`import { npm } from '@/modules/package-manager/npm'`,
но ядро `_/` — только изнутри: `import { core } from '../_/'`.

### Модуль со своими страницами и маршрутами

Если страницы принадлежат домену модуля, он может владеть ими — это позволяет
держать бóльшую часть API приватной:

```
modules/Auth/
  pages/
    login.tsx
  routes.ts
  index.ts     # экспортирует authRoutes, app собирает их в роутер
```

## Документирование и тестирование

- Каждому модулю — `README.md`: назначение, как использовать, ответственные.
  Это помогает и разработчикам, и AI-агентам.
- Модуль — самостоятельная единица: юнит-тесты изолированы от других модулей;
  интеграционные тесты — на уровне app.

## Лучшие практики

1. **Не дели избыточно.** Чем больше модулей, тем больше потенциальных связей.
   Микромодуль ради одного файла → лучше common или однофайловый модуль.
2. **Релевантность содержимого.** Всё, что не относится к домену модуля,
   выноси в common или другие слои — иначе границы размываются.
3. **Имена по домену:** `UserProfile`, `OrderHistory`, `AccessControl`.
   Плохо: `User`, `Data`, `Utils`, сокращения.
4. **Ответственные** — в README.md или MAINTAINERS.md модуля.

От дисциплины именно на этом уровне зависит, получится «big ball of mud»
или хорошо организованный проект.
