# Уровень Pages — страницы приложения

## Назначение

Pages определяет существующие страницы сайта. **Каждая страница соответствует
конкретному URL** — структура файлов напрямую отражает структуру маршрутов,
поэтому по папке pages можно мгновенно понять, какие URL есть в приложении.

Четыре задачи уровня:
1. **Определяют маршруты** — страница ↔ URL.
2. **Служат точками входа** — связывают URL с компонентами.
3. **Изолированы от бизнес-логики** — используют модули, не содержат сложную логику.
4. **Не переиспользуются** — уникальны; app импортирует их только для роутера.

Модули могут определять собственные маршруты, но pages — единственное место
для страниц, которые сложно отнести к конкретному модулю (404, About и т.п.).

## Правила именования файлов (конвенции файлового роутинга)

Файловый роутинг не обязателен, но соответствие путей — рекомендация FEOD:

| URL | Файл |
|-----|------|
| `/about` | `pages/about.tsx` |
| `/` | `pages/index.tsx` |
| `/products/` | `pages/products/index.tsx` |
| `/posts/123` | `pages/posts/[id].tsx` |
| `/posts/42_7` (два параметра) | `pages/posts/[userId]_[postId].tsx` |
| `/users/42/posts/7` | `pages/users/[userId]/posts/[postId].tsx` |
| `/docs/что-угодно/глубже` | `pages/docs/[...path].tsx` |
| любой несуществующий (404) | `pages/[...404].tsx` |

Named views (несколько компонентов на маршрут): `pages/login.form.tsx`,
`pages/login.content.tsx`.

## Приватные модули страниц (использовать редко!)

Если у страницы есть код, нужный только ей, можно создать приватный модуль
с префиксом `_`:

```
pages/
├── profile/
│   ├── _profile/            # приватный модуль страницы profile
│   │   ├── components/
│   │   │   └── ProfileHeader.tsx
│   │   ├── api/
│   │   └── index.ts
│   └── index.tsx
```

Правила: приватный модуль доступен ТОЛЬКО своей странице; не может
импортировать другие сущности уровня pages. Рекомендация FEOD — не
злоупотреблять и предпочитать обычные модули в `modules/`.

## Страницы должны быть тонкими

Страница = композиция модулей + обработка состояний. Вся логика — в модулях.

```tsx
// ✅ Хорошо: страница только компонует модуль
// pages/dictionary/index.tsx
import { observer } from 'mobx-react-lite'
import { WordList, dictionaryStore } from '@/modules/Dictionary'

export const DictionaryPage = observer(() => (
  <div>
    {dictionaryStore.loading && <Spinner />}
    {dictionaryStore.error && <ErrorBox message={dictionaryStore.error} />}
    {!dictionaryStore.loading && <WordList />}
  </div>
))
```

```tsx
// ❌ Плохо: бизнес-логика (фильтрация, запросы, SRS-расчёты) прямо на странице
```

## Лучшие практики

1. **Минимизируй логику в страницах** — используй модули.
2. **Переиспользуемую логику** выноси в сторы/хуки модулей.
3. **Всегда обрабатывай loading и error** состояния.
4. **Используй константы маршрутов** из `common/constants/routes.ts`,
   не хардкодь строки путей.

## FAQ

- **Можно не создавать pages вообще?** Да, если приложение чётко делится на
  модули — страницы могут жить внутри модулей (`modules/<X>/pages/`).
- **Вложенные маршруты?** Структура папок повторяет вложенность URL.
- **Layout для страницы?** Определяется в `app/layouts` и выбирается в
  роутере, НЕ внутри страницы.
- **404?** Catch-all: `pages/[...404].tsx`.
