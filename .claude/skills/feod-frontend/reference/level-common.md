# Уровень Common — тонкий слой общих сущностей

## Назначение

Common хранит сущности **для общего переиспользования, не привязанные к
бизнес-логике**, которые могут использоваться в любом месте проекта. Также
сюда попадают отдельные компоненты, которые сложно отнести к конкретному модулю.

Задачи уровня:
- решает проблему «модуль ради модуля» — не надо создавать полноценный модуль
  ради одной маленькой сущности;
- служит мягким переходом для разработчиков после FSD.

⚠️ Несмотря на сходство с `shared` из FSD, это ПРИНЦИПИАЛЬНО другой уровень
(см. таблицу отличий внизу).

## Критерии: сущность относится к common, если ВСЕ пункты верны

1. Логика НЕ привязана к конкретным бизнес-фичам (иначе — в модуль);
2. Вмещается **в один файл** (нужно несколько файлов — создавай модуль);
3. Теоретически может использоваться в любом месте проекта;
4. НЕ нуждается во взаимодействии с сущностями уровня modules
   (нужно — переноси в модуль или применяй IoC).

## Структура

```
common/
├── ui/                  # базовые компоненты (Button.tsx, Input.tsx)
├── hooks/               # useDebounce.ts, useLocalStorage.ts
├── utilities/           # formatDate.ts, validateEmail.ts
├── constants/           # routes.ts, cefr.ts
└── types/               # api.types.ts
```

Подпапки группируют сущности по типу; каждая сущность — один файл.

## Ключевые правила

### 1. Barrel-файлы (index.ts) ЗАПРЕЩЕНЫ

```typescript
// ✅ Правильно — прямой импорт из файла:
import { Button } from '@/common/ui/Button'
import { formatDate } from '@/common/utilities/formatDate'

// ❌ Неправильно — через индексный файл:
import { Button, formatDate } from '@/common'
```

Почему: нет файлов без смысловой нагрузки; меньше работы при создании
сущности; мотивирует использовать модули, когда они нужны; держит common
«тонким». Это настоятельная рекомендация — отступление требует серьёзного
обоснования.

### 2. Одна сущность = один файл

Несколько файлов на сущность — допустимо в редких случаях, но правильнее
создать модуль.

### 3. Взаимное использование

Common-сущности могут импортировать друг друга, если это не создаёт жёстких
связей между ними.

### 4. Нужен функционал модуля? — IoC, не импорт

```typescript
interface NotificationService {
  show(message: string): void
}

export function useNotification(service?: NotificationService) {
  const notify = service?.show ?? console.log
  return { notify }
}
```

## Когда выносить сущность из common в модуль

Common — «перевалочный пункт» для формирующихся структур; перенос — нормальный
процесс эволюции проекта. Сигналы:
- несколько common-сущностей тесно сцепились вокруг общей задачи;
- сущность обросла бизнес-логикой;
- потребовалось взаимодействие с другими уровнями (кроме globals);
- сущность разрослась на несколько файлов.

## UI-компоненты и дизайн-система

- Полноценная дизайн-система с тесно связанными элементами → отдельный модуль.
- Россыпь базовых компонентов без общей системы → может жить в `common/ui/`.
- Если модульному UI нужно быть доступным в common — IoC, либо задокументированное
  исключение (субоптимально).

## Отличия от shared (FSD)

| Аспект | Common (FEOD) | shared (FSD) |
|--------|---------------|--------------|
| Ориентация | на модули | на слои абстракции |
| Индексные файлы | запрещены | обязательны |
| Роль | перевалочный пункт перед модулем | постоянный слой |
| Перемещение сущностей | нормальный процесс | редкое явление |
| Организация | по логике и взаимодействию | по уровню абстракции |

В FEOD связанные сущности держатся вместе в модуле, а не разделяются по
слоям абстракции.
