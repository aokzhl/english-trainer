# FEOD — Fractal Entity Oriented Design

Методология организации структуры фронтенд-проектов (https://feod.dev).
Сочетает слоистый и модульный подходы.

**Три кита:**
1. **Модульность** — модуль = независимая часть проекта со своей структурой,
   правилами и поведением; рассматривается как зависимость (как npm-пакет).
2. **Фрактальность** — одни и те же правила действуют на любой глубине
   вложенности (модуль может содержать `modules/` с подмодулями).
3. **Сущность-ориентированность** — у каждого файла и папки есть роль, которая
   полностью определяет её поведение, наименование и правила.

## Уровни и цепочка импортов (ядро методологии)

```
client/src/
├── app/       # запуск и настройка приложения (bootstrap)
├── pages/     # страницы, привязанные к URL
├── modules/   # бизнес-логика, «сердце» приложения
├── common/    # общие однофайловые сущности без бизнес-логики
└── globals/   # глобальные типы, полифиллы, shims (без импортов)
```

**Направление импортов строго вниз:** `app → pages → modules → common`.
Верхние уровни знают о нижних, но не наоборот.

| Уровень | Может импортировать | Кем импортируется |
|---------|--------------------|-------------------|
| app     | pages, modules, common | никем |
| pages   | modules, common    | только app (для роутера) |
| modules | другие modules (ТОЛЬКО через их `index.ts`), common | pages, app, другие modules |
| common  | другие common-сущности (без жёстких связей) | modules, pages, app |
| globals | ничего             | никем — доступен глобально без импорта |

Любой импорт против направления (например, из `pages` внутри `modules`) —
архитектурная ошибка. Исправлять немедленно.

## Экспресс-решение «куда положить файл»

1. Связано со стартом/конфигурацией приложения и нигде не переиспользуется? → `app/`
2. Это страница с собственным URL? → `pages/` (тонкая: композиция модулей)
3. Бизнес-логика, несколько файлов, своя зона ответственности? → `modules/<Name>/`
4. Универсальная сущность в один файл, без бизнес-логики? → `common/`
5. Должно быть доступно без импорта (типы, полифилл, shim)? → `globals/`
6. Сомневаешься между common и modules: разрослось на несколько файлов или
   появилась бизнес-логика → модуль. Common — «перевалочный пункт», перенос
   сущностей из него в модули — нормальный процесс эволюции.

## Пять железных правил (нарушать нельзя)

1. Импорты только вниз по цепочке уровней.
2. Внутрь чужого модуля — только через его `index.ts` (публичный API).
3. В `common` нет barrel-файлов (`index.ts`) и многофайловых сущностей.
4. Страницы и app не содержат бизнес-логики — она в модулях.
5. Никаких обращений к подмодулям чужих модулей и «через голову»
   (к подмодулям своих подмодулей).

Осознанное отступление допустимо только с комментарием-обоснованием в коде
(«лучшее — враг хорошего»), но сначала попробуй IoC/реструктуризацию.
